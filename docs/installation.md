# Installation

`shk` is distributed as a single CLI binary.

## npm

Each tagged CLI release publishes an npm package. The names `shk` and `shk-cli` were already taken on the npm registry, so the package is published as [`security-harness-kit`](https://www.npmjs.com/package/security-harness-kit); the installed command is still `shk`:

```bash
npm install -g security-harness-kit
shk --version
```

The npm package is generated by `dist` from the same release. On install it fetches the matching prebuilt release archive for your platform and exposes the `shk` command, so it supports the same platforms as the release archives.

The install script needs Node.js 14.18 or later. Behind a proxy, set `HTTPS_PROXY` to an `http://` proxy URL; the script also reads `NO_PROXY`. It does not read `ALL_PROXY` or npm's own `proxy` and `https-proxy` settings. Write `NO_PROXY` entries as bare host names such as `github.com`, without a leading dot, wildcard, or port; each entry also covers its subdomains.

For one-off runs without a global install:

```bash
npx security-harness-kit scan
```

## bun

The same npm package works with bun. Its `postinstall` script fetches the platform binary at install time; if bun skips lifecycle scripts, the binary is fetched on the first run instead.

```bash
bun add -g security-harness-kit
shk --version
```

For one-off runs without a global install:

```bash
bunx security-harness-kit scan
```

## Install With Script

macOS and Linux releases can be installed with the bundled installer:

```bash
curl --proto '=https' --tlsv1.2 -LsSf https://github.com/Kazuki-tam/security-harness-kit/releases/latest/download/shk-cli-installer.sh | sh
```

Windows releases can be installed from PowerShell:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -Command "irm https://github.com/Kazuki-tam/security-harness-kit/releases/latest/download/shk-cli-installer.ps1 | iex"
```

`-ExecutionPolicy Bypass` is scoped to this one PowerShell process, so it avoids common script policy failures without changing the user's machine or profile policy. If you are already in PowerShell, this equivalent form also works:

```powershell
Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass -Force; irm https://github.com/Kazuki-tam/security-harness-kit/releases/latest/download/shk-cli-installer.ps1 | iex
```

If your organization enforces PowerShell through `MachinePolicy` or `UserPolicy`, the script installer may still be blocked. In that case, use the manual `.zip` install instead. It does not execute the downloaded installer script.

The installers are generated by `dist` and download the latest matching release archive. The shell installer verifies the selected archive against the SHA-256 checksum embedded at release time before installing `shk`. The generated PowerShell installer does not currently perform checksum verification; Windows users who require verification should use the [manual `.zip` installation](#manual-windows-zip-install) below. By default, script installers use the Cargo-style install path (`$CARGO_HOME/bin`, or `~/.cargo/bin` when `CARGO_HOME` is unset). For images, install to a directory on the default `PATH` instead; see [Containers And Sandboxes](#containers-and-sandboxes).

## Manual Windows Zip Install

If downloaded PowerShell scripts are blocked, install the Windows archive manually. These commands download the release `.zip`, unpack `shk.exe`, place it in the Cargo-style binary directory, add that directory to the user `PATH`, and verify the install:

```powershell
$Target = "x86_64-pc-windows-msvc"
$Repo = "Kazuki-tam/security-harness-kit"
$DownloadDir = Join-Path $env:TEMP "shk-download"
$ExtractDir = Join-Path $env:TEMP "shk-extract"
$InstallDir = if ($env:CARGO_HOME) { Join-Path $env:CARGO_HOME "bin" } else { "$env:USERPROFILE\.cargo\bin" }
$Zip = Join-Path $DownloadDir "shk-cli-$Target.zip"
$Checksum = "$Zip.sha256"

New-Item -ItemType Directory -Force -Path $DownloadDir, $ExtractDir, $InstallDir | Out-Null
Invoke-WebRequest "https://github.com/$Repo/releases/latest/download/shk-cli-$Target.zip" -OutFile $Zip
Invoke-WebRequest "https://github.com/$Repo/releases/latest/download/shk-cli-$Target.zip.sha256" -OutFile $Checksum
$Expected = ((Get-Content -Raw $Checksum) -split "\s+")[0].ToLowerInvariant()
$Actual = (Get-FileHash $Zip -Algorithm SHA256).Hash.ToLowerInvariant()
if ($Actual -ne $Expected) { throw "checksum mismatch: $Actual" }

Expand-Archive -Force $Zip $ExtractDir
Copy-Item (Join-Path $ExtractDir "shk.exe") $InstallDir -Force

$UserPath = [Environment]::GetEnvironmentVariable("Path", "User")
if (($UserPath -split ";") -notcontains $InstallDir) {
  $NewUserPath = if ($UserPath) { "$UserPath;$InstallDir" } else { $InstallDir }
  [Environment]::SetEnvironmentVariable("Path", $NewUserPath, "User")
}
if (($env:Path -split ";") -notcontains $InstallDir) { $env:Path += ";$InstallDir" }

shk --version
```

Open a new terminal after installation if `shk` is not found in the current session.

## Download A Release Archive

Tagged releases publish platform archives, per-archive checksums, installers, a Homebrew formula, maintainer WinGet manifests, and a CycloneDX SBOM:

```text
shk-cli-aarch64-apple-darwin.tar.xz
shk-cli-aarch64-unknown-linux-gnu.tar.xz
shk-cli-x86_64-apple-darwin.tar.xz
shk-cli-x86_64-pc-windows-msvc.zip
shk-cli-x86_64-unknown-linux-gnu.tar.xz
shk-cli-installer.sh
shk-cli-installer.ps1
shk-winget-manifests.zip
shk.rb
shk-cli-npm-package.tar.gz
*-dist-manifest.json
*.sha256
shk-sbom.cdx.json
```

Verify the archive before unpacking:

```bash
shasum -a 256 -c shk-cli-x86_64-unknown-linux-gnu.tar.xz.sha256
```

Each archive contains the `shk` binary.

Tagged releases generate GitHub artifact attestations for release assets. Verify a downloaded asset with the GitHub CLI:

```bash
gh attestation verify shk-cli-x86_64-unknown-linux-gnu.tar.xz \
  --repo Kazuki-tam/security-harness-kit
```

Release assets are also covered by GitHub artifact attestations.

## Verified Archive Install

For CI or security-sensitive environments, install from a pinned release tag and verify both the checksum and GitHub artifact attestation before placing the binary on `PATH`:

```bash
version=v0.7.7
target=x86_64-unknown-linux-gnu
asset="shk-cli-${target}.tar.xz"
repo=Kazuki-tam/security-harness-kit

gh release download "$version" -R "$repo" -p "$asset" -p "${asset}.sha256"
shasum -a 256 -c "${asset}.sha256"
gh attestation verify "$asset" -R "$repo"

tmp="$(mktemp -d)"
tar -xJf "$asset" -C "$tmp"
install -m 755 "$tmp/shk-cli-${target}/shk" "$HOME/.cargo/bin/shk"
```

Replace `target` with the archive that matches your platform. Avoid `latest` in CI so builds are reproducible and reviewable.

## Homebrew

Each tagged CLI release publishes the generated Homebrew formula to the public tap [`Kazuki-tam/homebrew-tap`](https://github.com/Kazuki-tam/homebrew-tap). Install with:

```bash
brew install Kazuki-tam/homebrew-tap/shk
```

Homebrew drops the `homebrew-` prefix, so the short form also works:

```bash
brew install kazuki-tam/tap/shk
```

The formula always tracks the latest release. To upgrade later, run `brew upgrade shk`.

To pin a specific release with Homebrew 6, tap the repository and extract that version from its history into a personal tap (pass the version without the `v` prefix):

```bash
brew tap kazuki-tam/tap
brew version-install kazuki-tam/tap/shk <version>
```

The formula file (`shk.rb`) is also attached to each release as an asset. Current Homebrew only loads formulae from taps, so `brew install --formula` with a URL or a local path is rejected; to use the asset, create a tap with `brew tap-new <user>/<repository>`, copy `shk.rb` into its `Formula/` directory, and install `<user>/<repository>/shk`.

Intel macOS, Apple Silicon macOS, Linux x86_64/aarch64, and Windows x86_64 are supported. Scoop manifests are not published by the current release pipeline.

## Containers And Sandboxes

Install `shk` into the image, in a directory on the default `PATH`, such as `/usr/local/bin`. AI hooks run `shk` by name, and the [default script install location](#install-with-script), `~/.cargo/bin`, reaches `PATH` only through shell profiles. A container command that starts without a login or interactive shell does not read them, so the hooks fail with `shk: not found`. Claude Code then [blocks every action](commands.md#shk-hooks-install-ai), or skips the scan if the hooks were installed before this behavior was added or Claude Code is older than v2.1.295.

### Dockerfile

```dockerfile
FROM debian:bookworm-slim

RUN apt-get update \
  && apt-get install -y --no-install-recommends ca-certificates curl xz-utils \
  && curl --proto '=https' --tlsv1.2 -LsSf https://github.com/Kazuki-tam/security-harness-kit/releases/latest/download/shk-cli-installer.sh \
    | SHK_CLI_UNMANAGED_INSTALL=/usr/local/bin sh \
  && shk --version \
  && rm -rf /var/lib/apt/lists/*
```

- **Run it as root:** writing to `/usr/local/bin` needs root, so switch to your unprivileged `USER` after this step. Every user in the image can then run `shk`.
- **Keep `xz-utils`:** release archives are `.tar.xz`, and slim images cannot unpack them without it. This also applies to the npm package.
- **Keep `shk --version`:** it fails the build if the download or the binary does not work, because a failed `curl` in the pipe does not stop the build by itself.
- **Pin the release:** replace `latest/download` with `download/vX.Y.Z` so that rebuilds stay reproducible. To verify the archive as well, follow the [verified archive install](#verified-archive-install), and place the binary in `/usr/local/bin` instead of `~/.cargo/bin`.
- **v0.7.6 and earlier:** add `libdbus-1-3` to the `apt-get install` list. These releases do not start without it. <!-- shk-version-pin -->

In a Node.js image, `npm install -g security-harness-kit` also places `shk` on the default `PATH`. `-slim` Node.js images need `xz-utils` installed first.

The CLI only needs glibc, so it runs in minimal images such as `debian:bookworm-slim`. musl-based images such as Alpine are not supported.

### Check The Image

Check from a non-login, non-interactive shell, because that is what a container command gets:

```bash
docker run --rm <image> sh -c 'command -v shk && shk --version'
```

Then run `shk doctor` from your project inside the container.

### Dev Containers

Build the image from a Dockerfile like the one above, saved next to `.devcontainer/devcontainer.json`:

```json
{
  "build": { "dockerfile": "Dockerfile" }
}
```

Avoid installing `shk` in `postCreateCommand`. By default, tools connect once `updateContentCommand` finishes, so a terminal can open before `postCreateCommand` is done, and Claude Code blocks actions until `shk` is installed.

### Docker Sandboxes

Add `shk` with a [kit](https://docs.docker.com/ai/sandboxes/customize/), an experimental `sbx` feature. It needs v0.7.7 or later: this kit adds only the `shk` binary, not the `libdbus-1-3` that earlier releases need. Create these two files: <!-- shk-version-pin -->

`shk-kit/shk-kit.yaml`:

```yaml
# syntax=docker/sandbox-kit:3
schemaVersion: "3"
kind: mixin
displayName: shk
```

`shk-kit/shk-kit.dockerfile`:

```dockerfile
FROM debian:trixie-slim AS build
RUN apt-get update && apt-get install -y --no-install-recommends ca-certificates curl xz-utils
RUN curl --proto '=https' --tlsv1.2 -LsSf https://github.com/Kazuki-tam/security-harness-kit/releases/latest/download/shk-cli-installer.sh \
    | SHK_CLI_UNMANAGED_INSTALL=/out/usr/local/bin sh \
  && /out/usr/local/bin/shk --version

FROM scratch
COPY --from=build /out/usr/local/bin/shk /usr/local/bin/shk
```

Then start the sandbox from your project:

```bash
sbx run claude --kit ./shk-kit
```

If the build fails with `OCI exporter is not supported for the docker driver`, create a builder that supports it and pass it to `sbx`. Turning on the containerd image store in Docker also fixes this.

```bash
docker buildx create --name sbx-kits --driver docker-container
```

```bash
BUILDX_BUILDER=sbx-kits sbx run claude --kit ./shk-kit
```

### What Works In A Container

Project hooks in a committed `.claude/settings.json` come with the repository, so you do not need to run `shk hooks install-ai` again in the container. Hooks installed with `--global` stay on the host unless you mount that file.

`shk scan` and the AI hooks do not use the secret store. With `[env].secret_store = "keyring"` (the default), `shk env` needs a Secret Service provider such as gnome-keyring in a running D-Bus session; in containers and on headless servers, use the [1Password backend](commands.md) instead.

## Cloud Agents

A cloud agent runs on a machine other than yours, so neither your local `shk` nor your user-level hooks come with it, including hooks installed with `--global`. For each tool, install `shk` where its hooks can run it by name, commit the project hooks and `shk.toml`, and then [check that the hooks run](#check-that-hooks-run). `shk hooks install-ai` needs a `shk.toml`, so run [`shk init`](commands.md#shk-init) first if the project does not have one.

Coverage differs by tool. This table reflects each vendor's documentation as of November 2026:

| Tool | Install `shk` with | Project hooks | If `shk` cannot run | Cloud limits |
|------|--------------------|---------------|---------------------|--------------------------|
| [Claude Code](#claude-code-cloud-sessions) | Setup script | `.claude/settings.json` | Prompts and matched tool calls are blocked (Claude Code v2.1.295 or later) | Not scanned: sessions with several repositories, and cloud threads in a project |
| [Cursor](#cursor-cloud-agents) | Dockerfile | `.cursor/hooks.json` | The action proceeds, unless you use `--fail-closed` | Not scanned: MCP tool calls, and early read-only turns |
| [GitHub Copilot](#github-copilot-cloud-agent) | `copilot-setup-steps.yml` (GitHub Actions sessions only) | `.github/hooks/shk-security.json` | `preToolUse` denies on a non-zero exit; a timeout proceeds | No documented way to preinstall `shk` in cloud sandbox sessions |

Before relying on these steps, run the check below in your own environment. Antigravity, Codex, Grok Build, OpenCode, and Windsurf are not covered here.

### Check That Hooks Run

`shk --version` only shows that the binary is installed. To confirm that the hooks fire, start a new session and ask the agent to run this command in a shell:

```bash
cat .env
```

Whether or not the file exists, the default action guard denies the command with this reason:

```text
shk action guard: secret_dump_command blocked
```

How to read the result:

- **A reason that starts with `shk action guard:`:** the hook ran.
- **A denial with any other reason:** `shk` may have failed to run. Claude Code, Copilot, and Cursor with `--fail-closed` can also deny an action when the hook itself fails.
- **A `No such file` error or the file's contents:** the hook did not run, it was installed with `--audit`, or `[action_guard]` in `shk.toml` is off or allows the command.

Where hooks do not run, a [CI scan](ci.md) still checks what reaches a pull request, but it does not see what the agent read or sent along the way.

### Claude Code Cloud Sessions

These steps apply to Anthropic-hosted environments.

1. Install the project hooks, then commit and push `.claude/settings.json` and `shk.toml`:

   ```bash
   shk hooks install-ai --tool claude-code
   ```

2. On the new-session screen at [claude.ai/code](https://claude.ai/code), open the environment selector under the message box, add or edit an environment, and select **Setup script**. The **Default** environment starts without one.

3. Paste this script and save:

   ```bash
   #!/bin/bash
   set -euo pipefail
   apt-get update
   apt-get install -y --no-install-recommends ca-certificates curl xz-utils
   curl --proto '=https' --tlsv1.2 -LsSf https://github.com/Kazuki-tam/security-harness-kit/releases/latest/download/shk-cli-installer.sh \
     | SHK_CLI_UNMANAGED_INSTALL=/usr/local/bin sh
   shk --version
   ```

4. Start a new session and [check that the hooks run](#check-that-hooks-run).

[Setup scripts](https://code.claude.com/docs/en/cloud-environments#setup-scripts) run as root on Ubuntu 24.04 before Claude Code starts.

- **Network access:** the default **Trusted** allowlist includes the hosts this script uses, and installs fail with **None**. With **Custom**, include the default domains, or allow at least `github.com`, `release-assets.githubusercontent.com`, and the Ubuntu package mirrors such as `archive.ubuntu.com` and `security.ubuntu.com`. Claude Code's documentation does not say how its GitHub proxy treats release downloads, so check the setup output if the download fails.
- **Failed installs:** `set -euo pipefail` and `shk --version` make the script exit non-zero if the install fails. The session then fails to start or starts without `shk`, and in the second case Claude Code [blocks prompts and matched tool calls](commands.md#shk-hooks-install-ai). Fix the script and start a new session.
- **Updates:** the result of the script is [cached](https://code.claude.com/docs/en/cloud-environments#environment-caching). It runs again when you change the script or the allowed hosts, or when the cache expires after about seven days, so `latest/download` does not pick up a new release right away. To control the version, pin it with `download/vX.Y.Z`; changing the pin rebuilds the cache for new sessions.

[Some sessions do not run repository hooks](https://code.claude.com/docs/en/settings#settings-in-cloud-sessions), and `shk` does not scan them. This applies to sessions with several repositories and to cloud threads in a project. `~/.claude/settings.json` and `.claude/settings.local.json` are not read in any cloud session.

### Cursor Cloud Agents

1. Install the project hooks with `--fail-closed`, then commit and push `.cursor/hooks.json` and `shk.toml`:

   ```bash
   shk hooks install-ai --tool cursor --fail-closed
   ```

2. Add `shk` to the Dockerfile of your environment, before any `USER` instruction. This example assumes a Debian or Ubuntu base image:

   ```dockerfile
   RUN apt-get update \
     && apt-get install -y --no-install-recommends ca-certificates curl xz-utils \
     && curl --proto '=https' --tlsv1.2 -LsSf https://github.com/Kazuki-tam/security-harness-kit/releases/latest/download/shk-cli-installer.sh \
       | SHK_CLI_UNMANAGED_INSTALL=/usr/local/bin sh \
     && shk --version
   ```

3. Point `.cursor/environment.json` at that file, then commit both and push them to the default branch. The path is relative to `.cursor`, so this example uses `.cursor/Dockerfile`:

   ```json
   {
     "build": { "dockerfile": "Dockerfile" }
   }
   ```

4. Start an agent and [check that the hooks run](#check-that-hooks-run) after it has started working in a writable environment.

[Cursor builds](https://cursor.com/docs/cloud-agent/setup) use the configuration on the environment's default branch. Cursor checks a personal saved environment first, then a team saved environment, and then `.cursor/environment.json`, which it uses only for single-repository runs. A saved environment reads the committed file only if its **environment.json location** points at it, and new environments start with that set to **None**. Self-hosted machines never read the file. Cursor does not document which user the `install` command runs as, which is why this guide uses a Dockerfile. Cursor manages the checkout, so do not `COPY` the project into the image.

- **Why `--fail-closed`:** by default, [Cursor lets an action proceed](https://cursor.com/docs/agent/hooks) when a hook crashes, times out, or exits with a code other than `2`, so without `shk` the agent keeps working with no scan. The flag blocks the action instead, for everyone who uses the committed file, so install `shk` for your team first. Re-running `shk hooks install-ai --tool cursor` without the flag turns it off.
- **MCP tool calls:** `beforeMCPExecution` and `afterMCPExecution` do not run in cloud agents, so `shk` does not scan MCP calls there.
- **Early turns:** hooks do not run during early exploratory turns in a read-only environment.
- **User-level hooks:** `~/.cursor/hooks.json` is not available.

### GitHub Copilot Cloud Agent

Copilot sessions can run in a cloud sandbox, on GitHub Actions, or in a custom environment you manage. [Setup steps](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/customize-cloud-agent/customize-the-agent-environment) apply only to sessions on GitHub Actions. Cloud sandbox sessions do not read them, and GitHub does not document another way to preinstall tools there, so this guide covers GitHub Actions sessions. In a custom environment, install `shk` as part of that environment.

1. Install the project hooks, then commit `.github/hooks/shk-security.json` and `shk.toml` and merge them. The hooks file must be on the default branch for Copilot cloud agent to use it:

   ```bash
   shk hooks install-ai --tool copilot
   ```

2. Create `.github/workflows/copilot-setup-steps.yml` on the default branch. The job must be named `copilot-setup-steps`:

   ```yaml
   name: "Copilot Setup Steps"

   on:
     workflow_dispatch:

   jobs:
     copilot-setup-steps:
       runs-on: ubuntu-latest
       permissions:
         contents: read
       steps:
         - name: Checkout code
           uses: actions/checkout@v6

         - name: Install shk
           run: |
             sudo apt-get update
             sudo apt-get install -y --no-install-recommends xz-utils
             curl --proto '=https' --tlsv1.2 -LsSf https://github.com/Kazuki-tam/security-harness-kit/releases/latest/download/shk-cli-installer.sh \
               | sudo env SHK_CLI_UNMANAGED_INSTALL=/usr/local/bin sh
             shk --version
   ```

3. Start a session on GitHub Actions and [check that the hooks run](#check-that-hooks-run).

GitHub's [setup steps guide](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/customize-cloud-agent/customize-the-agent-environment) and [hooks reference](https://docs.github.com/en/copilot/reference/hooks-reference) describe this behavior in the cloud:

- **Failures:** a non-zero exit from a command `preToolUse` hook denies the tool call, so expect tool calls to be denied wherever the committed hooks load without `shk`, including cloud sandbox sessions. If a setup step fails, Copilot skips the remaining steps and starts anyway. A hook timeout is different: the tool call proceeds. `shk` sets a 30-second timeout on these hooks.
- **Permission requests:** `PermissionRequest` has no effect in the cloud because tool calls are pre-approved. `preToolUse` does the blocking.
- **Audit logs:** files written by hooks are discarded when the job ends, including `.shk/audit.log` from `--log-blocked`.
- **User-level hooks:** the sandbox does not ship with user-level hook files, so `~/.copilot/hooks/` does not apply.

## Desktop App

The desktop app is distributed separately from the CLI. The hooks that Quick
Setup installs run the `shk` command, so the CLI must also be installed for
real-time protection; everything else in the app works on its own. Releases
are published from `desktop-vX.Y.Z` (or combined `shk-vX.Y.Z`) tags as `shk-desktop_*` assets
on GitHub Releases. Starting with `desktop-v0.6.0`, macOS builds are <!-- shk-version-pin -->
Developer ID signed, notarized, and stapled. Windows installers are currently
**not** Authenticode-signed (see
[Windows SmartScreen](#windows-smartscreen) below).

See [`desktop-release.md`](desktop-release.md) for maintainer release steps.

The Mask screen can redact (`[REDACTED]`) or pseudonymize (consistent codes)
content before it goes to an AI tool. Pseudonymize needs a project with
`shk.toml` selected because the key that keeps codes consistent is stored per
project, in the same credential store the CLI uses; the first run from the app
asks before creating it, and macOS may ask once before the app can read a key
the CLI created (or the other way round), since they are separate signed
binaries. See [`shk mask --pseudonymize`](commands.md#shk-mask) for the
underlying behaviour and restore maps.

| Platform | Asset pattern | Notes |

`shk-desktop-latest.json`, whose `release_tag` says which versioned release the
stable files currently come from. The files are byte-identical to the
`shk-desktop_*` assets of that release, so its provenance attestation verifies
them too.

Verify a stable download:

```bash
curl -LO https://github.com/Kazuki-tam/security-harness-kit/releases/download/desktop-latest/shk-desktop-aarch64-apple-darwin.dmg
curl -LO https://github.com/Kazuki-tam/security-harness-kit/releases/download/desktop-latest/shk-desktop.sha256sum
awk '$2 == "shk-desktop-aarch64-apple-darwin.dmg"' shk-desktop.sha256sum \
  | shasum -a 256 -c -
```

To pin a specific version instead, download the versioned `shk-desktop_*`
assets and `shk-desktop.sha256sum` from that tag's release page, for example
[desktop-v0.6.4](https://github.com/Kazuki-tam/security-harness-kit/releases/tag/desktop-v0.6.4). <!-- shk-version-pin -->

### macOS

Installers from `desktop-v0.6.0` onward are Developer ID signed <!-- shk-version-pin -->
and notarized;
Gatekeeper opens them without workarounds. If you still run an older unsigned
early access build, replace it with a signed `.dmg` install — the in-app
updater also migrates existing installs because all releases share the same
Tauri updater signing keys.

### Windows SmartScreen

Windows installers are currently not Authenticode-signed, so SmartScreen may
show **Windows protected your PC**. Choose **More info → Run anyway** if you
trust the release checksum and attestation.

### Blocked-activity notifications

While the app is open it tails `.shk/audit.log` for every project in the
sidebar and raises an OS notification when a hook blocks AI activity, so an
agent running in the background is visible without switching to the app. The
bell menu in the top bar turns notifications off, or narrows them to one kind
of block; both kinds are on by default.

Details worth knowing:

- Only blocks recorded **after** a project appears in the sidebar are
  announced — existing history never produces a backlog of notifications.
- Blocks arriving within a few seconds collapse into a single notification.
- Notification text is limited to the block reason, the risky-action category,
  and the AI tool. File paths are deliberately left out, because notifications
  render on the lock screen and are persisted by the OS; use the **Blocked AI
  activity** panel to see them.
- Turning notifications off stops the banners, not the tailing: the audit panel
  still updates while the app is open.
- The first block prompts for OS notification permission (on macOS the
  installed app appears as **shk**; a `tauri dev` binary sends through the
  **Terminal** identity instead, so allow Terminal notifications when testing).
- No banner but blocks listed in the panel almost always means macOS is
  suppressing display: check Focus mode, and the per-app notification style in
  System Settings → Notifications.

### In-app updates

The desktop app checks `desktop-latest/latest.json` on GitHub for updater
metadata. Updater packages are always signed with the project Tauri updater
key, independent of OS code signing.

### Unsigned early access builds (historical)

Before `desktop-v0.6.0`, builds were published unsigned from <!-- shk-version-pin -->
`desktop-unsigned-vX.Y.Z` tags (last: `desktop-unsigned-v0.5.5`). Those
required Gatekeeper / SmartScreen workarounds documented in their release
notes. The unsigned release path still exists for maintainers but is no longer
the recommended install.

## Build From Source

Building from source requires Rust 1.90 or newer.

```bash
git clone https://github.com/Kazuki-tam/security-harness-kit.git
cd security-harness-kit
cargo build --release
```

The release binaries are written to:

```text
target/release/shk
```

## Uninstall

`shk` does not ship a dedicated `shk uninstall` command. Removal has two layers: the CLI binary, and any project or user-level files written by `shk` while it was in use.

Remove managed Claude Code hooks before the binary. Otherwise Claude Code blocks prompts and tool calls in those projects, or in every project for a `--global` install, until the entries are removed. See [step 2](#2-remove-project-artifacts).

### 1. Remove The Binary

Pick the method that matches how `shk` was installed.

Script installer (default `~/.cargo/bin`):

```bash
rm -f "${CARGO_HOME:-$HOME/.cargo}/bin/shk"
```

Windows (PowerShell installer; default `%USERPROFILE%\.cargo\bin` when `CARGO_HOME` is unset):

```powershell
$BinDir = if ($env:CARGO_HOME) { Join-Path $env:CARGO_HOME "bin" } else { "$env:USERPROFILE\.cargo\bin" }
Remove-Item (Join-Path $BinDir "shk.exe") -ErrorAction SilentlyContinue
```

Homebrew formula:

```bash
brew uninstall shk
# If installed from a tap, you can also remove it:
# brew untap Kazuki-tam/homebrew-tap
```

npm package:

```bash
npm uninstall -g security-harness-kit
```

Release archive: remove `shk` from the directory where you unpacked or copied it.

bun:

```bash
bun remove -g security-harness-kit
```

Source build: run `cargo clean` in the cloned repository to remove build output, or remove `target/release/shk` directly. If you copied that binary into a directory on `PATH`, remove the copied binary there as well.

### 2. Remove Project Artifacts

`shk` does not modify project files unless you explicitly run a command that writes to disk. The artifacts created by those commands are listed below. Remove any that you no longer need from each project.

| Source | Path | Notes |
|--------|------|-------|
| `shk init` / `shk policy init` | `shk.toml` | Project policy file. |
| `shk init` with npm hardening | `.npmrc`, `pnpm-workspace.yaml`, `.yarnrc.yml`, `bunfig.toml` as applicable | Project package-manager hardening files. Remove only settings added for `ignore-scripts` or package age gates if the file also contains your own package-manager configuration. |
| `shk scan --audit`, audit-mode hooks | `.shk/audit.log` and the `.shk/` directory | Metadata-only audit log. |
| `shk hooks install` | `.git/hooks/pre-commit` | Managed block delimited by `# shk-managed-start` / `# shk-managed-end`. Delete the file if `shk` is the only owner, or remove just the managed block to keep other pre-commit logic. |
| `shk hooks install-ai` (Claude Code) | `.claude/settings.json` (global: `~/.claude/settings.json`) | Remove entries tagged with `"_shk_managed": true`. Delete the file if it has no remaining entries. If you used `--apply-deny` or `--apply-sandbox`, also review the `permissions.deny` and `sandbox` settings that were merged into the same file. |
| `shk hooks install-ai` (Cursor) | `.cursor/hooks.json` | Remove entries tagged with `"_shk_managed": true`. |
| `shk hooks install-ai` (Codex) | `.codex/config.toml` | Remove the block delimited by `# shk-managed-start` / `# shk-managed-end`, and `features.hooks = true` if no longer needed. The managed block covers `PreToolUse`, `PermissionRequest`, `UserPromptSubmit`, and `PostToolUse`. If you used `--apply-sandbox`, also review the top-level `sandbox_mode` and `approval_policy` values. |
| `shk hooks install-ai` (Copilot) | `.github/hooks/shk-security.json` | Remove entries whose command contains `shk scan --hook-mode copilot`. |
| `shk hooks install-ai` (Antigravity) | `.agents/hooks.json` | Remove the top-level `shk-security` entry (its hook entries are tagged with `"_shk_managed": true`). Delete the file if it has no remaining entries. |
| `shk hooks install-ai` (Grok Build) | `.grok/hooks/shk-security.json` | Remove handlers whose command contains `shk scan --hook-mode grok`, and any matcher groups left empty. Delete the file if it has no remaining entries. |
| `shk hooks install-ai` (OpenCode) | `.opencode/plugins/shk-security.js` | Managed plugin file (starts with `// shk-managed:`). Delete the file; OpenCode discovers plugins by directory, so nothing else references it. OpenCode itself may have created `.opencode/package.json`, `.opencode/node_modules/`, and `.opencode/.gitignore` for its plugin SDK; those are not shk's. |
| `shk hooks install-ai` (Windsurf) | `.windsurf/hooks.json` | Remove entries whose command contains `shk scan --hook-mode windsurf`. Delete the file if it has no remaining entries. |
| `shk skills install` (Claude Code) | `.claude/skills/shk/SKILL.md` | Bundled skill file. Installs from 0.3.17 or earlier used `.claude/skills/shk.md`; remove that file too if present. |
| `shk skills install` (Copilot) | `.github/skills/shk/SKILL.md` | Bundled skill file. |
| `shk skills install` (Codex / Cursor / Antigravity / OpenCode) | `.agents/skills/shk/SKILL.md` | Bundled skill file. |
| `shk skills install` (Grok Build) | `.grok/skills/shk/SKILL.md` | Bundled skill file. |
| `shk skills install` (Windsurf) | `.windsurf/skills/shk/SKILL.md` | Bundled skill file. |
| `shk ci init github` | `.github/workflows/shk.yml` by default | Generated GitHub Actions workflow. If you passed `--output`, remove that custom path instead. |

For commands that support it, re-running with `--dry-run` is a safe way to confirm the exact paths used in your project before deleting them. This applies to `shk hooks install-ai`, `shk skills install`, and `shk ci init github`; `shk hooks install` and `shk init` do not have a dry-run mode.

### 3. Remove User-Level Files

`--global` installs write to the user's home directory instead of the project. Remove these only if you want to disable `shk` for every project on this machine.

| Source | Path |
|--------|------|
| `shk hooks install-ai --global --tool claude-code` | `~/.claude/settings.json` (managed entries, plus any `permissions.deny` or `sandbox` settings you explicitly enabled) |
| `shk hooks install-ai --global --tool codex` | `~/.codex/config.toml` (managed block, plus top-level sandbox settings if you used `--apply-sandbox`) |
| `shk hooks install-ai --global --tool cursor` | `~/.cursor/hooks.json` (managed entries) |
| `shk hooks install-ai --global --tool copilot` | `~/.copilot/hooks/shk-security.json` (managed entries) |
| `shk hooks install-ai --global --tool antigravity` | `~/.gemini/config/hooks.json` (managed `shk-security` entry) |
| `shk hooks install-ai --global --tool grok` | `~/.grok/hooks/shk-security.json` (managed entries identified by `--hook-mode grok`) |
| `shk hooks install-ai --global --tool opencode` | `~/.config/opencode/plugins/shk-security.js` (managed plugin file; `$XDG_CONFIG_HOME/opencode/plugins/` when that is an absolute path) |
| `shk hooks install-ai --global --tool windsurf` | `~/.codeium/windsurf/hooks.json` (managed entries identified by `--hook-mode windsurf`) |
| `shk skills install --global --tool claude-code` | `~/.claude/skills/shk/SKILL.md` (or the legacy `~/.claude/skills/shk.md` from 0.3.17 or earlier) |
| `shk skills install --global --tool codex` / `--tool cursor` / `--tool opencode` | `~/.agents/skills/shk/SKILL.md` |
| `shk skills install --global --tool copilot` | `~/.copilot/skills/shk/SKILL.md` |
| `shk skills install --global --tool antigravity` | `~/.gemini/config/skills/shk/SKILL.md` |
| `shk skills install --global --tool grok` | `~/.grok/skills/shk/SKILL.md` |
| `shk skills install --global --tool windsurf` | `~/.codeium/windsurf/skills/shk/SKILL.md` |

Managed entries use the same markers as project installs (`"_shk_managed": true` for JSON files, `# shk-managed-start` / `# shk-managed-end` for shell and TOML files). Copilot, Grok Build, and Windsurf keep schema-clean JSON and are identified by their `--hook-mode <tool>` command strings; the OpenCode plugin file starts with a `// shk-managed:` header. Settings merged by `--apply-deny` and `--apply-sandbox` are not individually tagged; review them before removing so you do not discard unrelated user configuration.

### 4. Remove Stored Env Keys

If you used `shk env dotenvx import-keys` or `shk env key import` / `shk env encrypt`, delete stored private keys before removing the binary so they are not orphaned. Stored keys are scoped to the canonical project root, so run this from each project where keys were stored:

```bash
shk env dotenvx delete --all
shk env key delete --all
```

When `[env].secret_store = "keyring"` (the default), dotenvx keys live under the OS credential service `security-harness-kit/dotenvx`, and native keys live under `security-harness-kit/env`. If `shk` has already been removed, search for those service names in the platform credential store UI.

When `[env].secret_store = "1password"`, keys are stored as tagged 1Password items (`shk` tag) in the vault configured by `env.onepassword.vault`. Item titles look like `shk:{project_id}:env:DOTENV_PRIVATE_KEY` or `shk:{project_id}:dotenvx:DOTENV_PRIVATE_KEY_PRODUCTION`. Delete them from the vault UI, or migrate back to the keyring first:

```bash
shk env key migrate --to keyring
```

Verify the keyring copy, then remove the old tagged items explicitly from 1Password. Automatic source deletion is intentionally refused for a shared 1Password source.
