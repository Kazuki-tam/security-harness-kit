## Read before upgrading

### Claude Code hooks now block actions when `shk` cannot run

Managed `PreToolUse` and `UserPromptSubmit` hooks now set `"onFailure": "block"`. If `shk` is missing, cannot start, or times out, Claude Code blocks the tool call or prompt. Until now, it let the action proceed without a scan, so a session could lose its protection with no visible sign. ([#420](https://github.com/Kazuki-tam/security-harness-kit/pull/420))

Upgrading the binary does not change your settings. The new behavior starts when hooks are refreshed by any of these:

- `shk hooks install-ai --tool claude-code`
- `shk init`
- The "Refresh Claude Code managed hooks" fix in the desktop app

**Shared settings are affected the most.** After someone refreshes the hooks and commits `.claude/settings.json`, Claude Code stops in every environment that uses the project without `shk` on its `PATH`:

- Teammates who have not installed `shk`
- Claude Code cloud sessions and CI runners
- Containers, where the default install location `~/.cargo/bin` is usually not on `PATH`
- GUI-launched clients that do not inherit your shell `PATH`

Prompts are blocked too, so Claude Code cannot help fix this from inside the session. In non-interactive CI, check the job's output as well as its result: on Claude Code 2.1.318, `claude -p` exited `0` after its prompt was blocked, so a job can pass without doing any work.

**Before committing refreshed hooks,** install `shk` in those environments. [Containers And Sandboxes](https://github.com/Kazuki-tam/security-harness-kit/blob/main/docs/installation.md#containers-and-sandboxes) covers images, dev containers, Docker Sandboxes, and cloud sessions.

**To recover from a block,** do one of the following from a terminal or editor:

| Option | Effect | Who it affects |
|---|---|---|
| Install `shk` or fix its `PATH` (recommended) | Scanning resumes and protection stays on | The current environment |
| Change `"block"` to `"continue"` in `.claude/settings.json` | Findings still block, but actions proceed without a scan when `shk` cannot run | Everyone, once committed |
| Remove the entries tagged `"_shk_managed": true` | `shk` no longer scans anything in Claude Code for this project | Everyone, once committed |

If you are the only one blocked on a committed file, install `shk` rather than editing the file. After a `"continue"` edit, `shk doctor` keeps warning, and running `install-ai` again restores `"block"`.

Other details:

- **Global installs:** with `--global`, removing `shk` blocks every project on the machine. Remove the managed hooks before the binary. `shk doctor` only reads the project's settings, so it does not report global installs.
- **`--log-blocked` and `--audit`:** pass the same flag again when you re-run `install-ai` or `shk init`. A plain `install-ai` removes `--log-blocked` and turns an `--audit` install into a blocking one. The desktop fix keeps these flags.
- **Claude Code version:** blocking needs v2.1.295 or later. Older versions ignore the field and let actions proceed.

### `shk doctor --strict` can fail after upgrading

`shk doctor` now warns when a managed Claude Code hook lacks `"onFailure": "block"`. `--strict` treats that warning as a failure, so a CI job that passed on v0.7.6 exits `1` on v0.7.7 with no change to your repository. Jobs that install `shk` from `latest` pick this up without a version change. Plain `shk doctor` still exits `0`.

To fix it, re-run the install and commit the result:

```sh
shk hooks install-ai --tool claude-code
```

**That commit also turns on the blocking described above for everyone using the project,** so install `shk` in those environments first. If you need more time, keep CI on v0.7.6 or remove `--strict` for now.

The other edits do not suit this case. A `"continue"` edit still fails `--strict`. An `--audit` install passes, but it turns off all blocking.

## Fixed

- **Linux CLI runs in containers without `libdbus`.** v0.7.6 exited with status 127 on images without `libdbus-1.so.3`, including `node:22`, `ubuntu:24.04`, and the Docker Sandboxes template. The CLI now needs only the C runtime. Alpine and other musl images remain unsupported. ([#419](https://github.com/Kazuki-tam/security-harness-kit/pull/419))

## Changed

- **Linux key store backend.** Key storage now uses a pure-Rust Secret Service backend. Keys saved by v0.7.6 read correctly on gnome-keyring in our tests. Error messages from the store use new wording, so update any script that matches them. ([#419](https://github.com/Kazuki-tam/security-harness-kit/pull/419))
